# Skills

Skills are reusable instructions the assistant follows when a request matches. Settings → Skills has two views: **Installed** (search, filters All/On/Built in/From catalogs/Yours, a page per skill with its availability, instructions, edit and remove) and **Explore catalogs**. `surface-design` is a required built-in: its card says **Always on**, its detail has no off/remove control, and runtime checks enforce that state.

For new or revised workflows, start with [the authoring guide](SKILL-AUTHORING.md). It covers canonical data, layout, chart selection, both projections and the source map.

## Format

A skill is a `SKILL.md` file: a `---` block with `name` (lowercase letters, digits and single hyphens; up to 64) and `description` (when to use it; up to 1024 characters), then the instructions (up to 32 KB). Optional `license`, `compatibility`, string-valued `metadata` and `allowed-tools` are shown in Settings. Catalog skills may carry reviewed supporting UTF-8 text, including references, templates and script source. Files must have no NUL, use safe relative paths (at most eight segments and 200 characters), and fit 256 KiB each, 2 MiB and 50 files per skill. Binary assets are listed at review but omitted. Source files can be inspected and read as inert references; the skill loader never runs them.

The [Agent Skills format](https://agentskills.io/specification) is the package baseline; [ADR-040](ADR.md#adr-040-standard-skill-packages-app-owned-capabilities-2026-10-27) records the extensions and present limits. The parser supports standard frontmatter fields (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` / `allowed_tools`), plain, single-quoted and double-quoted scalar fields with inline comments, folded/literal block scalars (`>`, `|`, `>-`, `|-`) with flexible indentation, and flexible string metadata mappings without an external YAML dependency. Unsupported YAML constructs (nested objects, lists under metadata, aliases) are rejected cleanly. Standard directory layout (`references/`, `scripts/`, `assets/`) and root-level `SKILL.md` catalog packages are supported. On-disk local skill folders placed in `<data>/skills/<name>/` with a `SKILL.md` are automatically discovered with their `files/` supporting files. The experimental `allowed-tools` field discloses declared tools in activation output but never grants runtime access or bypasses user approvals. Full arbitrary YAML tags, binary assets and automatic execution of bundled skill scripts are outside the supported subset. Explicit isolated command/script execution uses the separate governed sandbox integration.

## How skills chain

- The system instructions carry only the name and description of each **enabled** skill.
- In app chat and tasks, the first counted model generation offers only skill selection. `use_skill` accepts `{names: [...]}` to select/load relevant enabled skills or `{names: []}` for no match. Answer and external tools are withheld during selection. Further calls can load additional skills. This uses the existing tool loop, not an extra hidden provider call.
- Changing enabled skills after a run is prepared fails explicitly if its selection context is stale, instead of bypassing selection.
- Schema-capable providers constrain the selection; other providers get one native selection tool with validation before dispatch. Invalid, interrupted or cancelled selection does not unlock answer tools. Task budgets, provider usage and conversation records include selection. This guarantees a selection step, not that the selected skills or resulting answer are semantically correct.
- Trusted local context loading uses answer-step limits and stays available when external-operation allowance is zero. It records no external operation; the selection generation is still metered. Further skill loads use the same bounded loop, without a fixed extra stage per skill.
- When a loaded skill has supporting files, `use_skill` lists their names and sizes. `read_skill_file` reads one file from a skill loaded in that run, at most 16,000 characters per page with an offset for more. It cannot read a merely enabled, disabled or unrelated skill. File text is reference data and never grants permissions.
- Skills never grant access: integration tools keep their policies and approvals. Scheduled tasks get `use_skill` alongside their selected capabilities.
- Voice and channel provider requests receive required surface-design guidance whenever the surface authoring contract is present. Optional skill selection remains separate; channel-specific tool and approval behavior is otherwise unchanged.

## Data and execution

The interactive-ui skill teaches related views mapped from one collection of records, with separate datasets for unrelated views, with form controls bound to canonical input pointers. It describes requested operations and submission behavior. The runtime uses typed component descriptors and resolves maps and supported aggregates; it never executes expression strings. Per-row calculations need an available tool or independently checked model-authored results.

The source-specific CSV bridge, derive/prepare tools, parameter options and automatic form/report compiler are removed. There is one general authoring path; ordinary task input snapshots and governed external tool results remain available as untrusted data. Validation, permissions, canonical persistence, revision checks and output receipts remain execution code.

Skill selection is verified separately from answer correctness. Historical local trials and the current authorized provider comparison are in [EVALUATION.md](EVALUATION.md). No provider result implies a platform reliability threshold. The installed app now uses the verified cleanup build; source edits alone still require a rebuild/restart before becoming installed behavior. Built-ins are seeded once; existing files are never silently replaced. Updates are reviewed explicitly, and edited/removed skills stay preserved until the user chooses a replacement. Catalog skills remain pinned to their reviewed version; built-in update availability does not claim an upstream catalog check.

## Catalog and review

- Six publisher repositories are listed (`shared/skills.ts`, checked October 2026); any public `owner/repository` can be opened.
- Listings are read at the repository's newest commit at least 14 days old, the same age rule integrations follow. The commit is recorded with the skill.
- Review lists each bundled file with its classification and size, including files beside a root-level SKILL.md. Expand an eligible text or script source file to see its exact content. Binary assets, unsupported types, invalid text and over-limit files remain listed with the reason and are not stored. Scripts are stored as text and never run by skill loading.
- Adding requires an acknowledgement covering the instructions and eligible text files. The fingerprint binds the repository, path, pinned commit, instructions and every added file hash. Added skills start off. Editing instructions keeps files; renaming moves them; removal deletes them. Every supporting-file read verifies its stored hash.
- The installed detail retains a list of files omitted at review. When a package needs those files, its instructions may be incomplete in this app; the review and detail pages say so.

Data: `<data>/skills/<name>/SKILL.md`, supporting text and inert source files under `<data>/skills/<name>/files/`, and `<data>/skills/skills.json` (on/off state, source and file manifest). Editing a skill starts from its exact stored `SKILL.md` text so optional frontmatter survives.

## Updates

New bundled packages seed once with supporting text. Existing built-ins whose instructions or file manifest differ from the current bundle appear under **Updates**, with an **Update available** badge. Their detail page shows both versions and current/proposed supporting files; **Update skill** replaces the package only after that explicit choice and preserves on/off state. A changed file or offered version invalidates the old preview. Removed skills are not restored. Catalog skills remain on their reviewed commit; automatic upstream checks/replacements are not implemented.
