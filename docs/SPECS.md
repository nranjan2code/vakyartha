# SPECS.md: Vakyartha

What the app is and how it is built. Rules: [AGENTS.md](../AGENTS.md). State of work: [HANDOVER.md](HANDOVER.md). Releasing: [RELEASING.md](RELEASING.md).

Agent MVP planning: [MVP-SPECS.md](MVP-SPECS.md) defines the proposed task experience and preserves the existing interactive, multi-surface design. [MVP-CHECKLIST.md](MVP-CHECKLIST.md) tracks existing foundations, design decisions, MVP gates and later scope. These are planning documents; the implementation described below remains the current baseline.

Vakyartha is a desktop app (macOS first) where a model's answers are interfaces: cards, tables, charts, forms and buttons. It is a product built on the [Projection framework](https://github.com/nranjan2code/Projection) (the `@vak/*` packages); the engine, catalog, projectors, providers, host and MCP client are the framework's, and are specified in [Projection's SPECS.md](https://github.com/nranjan2code/Projection/blob/main/SPECS.md). This document covers only what the app adds.

## 1. The framework dependency

- **One way only.** The app imports `@vak/*`; the framework never imports, builds or tests the app.
- **How it is pinned.** `framework/` is a git submodule of `github.com/nranjan2code/Projection`, pinned to one commit (a release tag once Projection tags them). npm workspaces link `framework/packages/*` into `node_modules/@vak/*`, so the app runs the framework's TypeScript sources directly in development, and the release bundles them into the sidecar.
- **What the app uses:** `@vak/host` (sessions, chat, approvals, token auth, `/api/project`), `@vak/providers` (provider registry, keys, profiles), `@vak/web` (`<vak-surface>`, `VakClient`), `@vak/core`, `@vak/mcp/client` (`Integrations`: installing, configuring and running servers), `@vak/telegram` (`runTelegram` for the Telegram channel).
- **What stays in the app:** anything that is a product decision: key storage, settings, the integrations catalog (which servers, versions, descriptions), channels, FinOps, Canvas and Artifacts, themes, the shell. A general engine need goes to Projection first (see [RELEASING.md](RELEASING.md), "Updating Projection").

## 3. Architecture

Tauri 2 shell, Vite + plain TypeScript UI, the engine as a Node sidecar. **The browser version is the same app**: `scripts/web.ts` (`npm run web`) runs the same app server (`sidecar/server.ts`) open on loopback :5178 and serves the same built UI, so there is one interface.
- **Sidecar** (`sidecar/`): `@vak/host` on an ephemeral loopback port with a random token. Keys in the macOS Keychain via `/usr/bin/security` (writes through stdin, never argv; older file-stored keys move over on start); elsewhere a 0600 file. Logs to `logs/engine.log` in the data folder, including UI errors (`/api/client-log`). Routes: settings, channels, integrations, approvals (host), client-log, info.
- **Attachments** (`sidecar/attachments.ts`): images and supported audio/video attached in the message box are posted as base64 JSON and saved to `<data>/attachments/<chat id>/<uuid>.<ext>` (folder 0700, files 0600, 20 MB). Recording/video signatures are checked. The message carries a typed attachment name/path for tools; the bubble shows only the name. Deleting the chat removes its folder; unsent attachments stay until that chat id is deleted.
- **Media plugins** (`sidecar/media/`, `src/media-page.ts`): independent Images, Audio and Video entries use the existing integrations lifecycle and per-tool policies. Provider/model choices are per operation and share provider/Voice keys. Standard HTTP adapters and canonical Voice adapters perform bounded work; the app owns private assets and a versioned job journal. Known provider IDs allow explicit status recovery; uncertain submissions are not automatically replayed. Results publish through the canonical host/store into dedicated screen/voice media projections, with authenticated asset resolution and local playback controls. Image/video results prefer the canvas; audio can stay inline. In conversation mode media-overlapping speech is discarded before transcription. No new package, native runtime or IPC. Exact supported operations, deletion scope, cost and verification limits: [MEDIA-TOOLS.md](MEDIA-TOOLS.md).
- **Integrations** (`sidecar/integrations.ts`): the app's curated catalog covers public-page reading, time, local image text extraction, scoped files, persistent memory, web research, repositories, pages, library documentation and governed workspace data/tools. The framework's `Integrations` (`@vak/mcp/client`) owns installation and execution: npm servers use exact pinned versions and script-free installs (`--ignore-scripts --before=<today − 14 days>`) into their own folders; hosted servers use HTTP transport with app-configured HTTPS destinations and declared credential headers. Workspace endpoints resolve from non-secret setup through the public framework API; the app validates the allowed hosts and MCP paths before saving or connecting. Only declared keys reach servers; folder checks, per-tool policies and approvals remain in force. User-added servers are marked unverified and calls are logged to `logs/tools.jsonl`. Time is on from the first run; other entries require setup/activation. Keys use the app's secret store. Settings → Integrations shows a marketplace (original icons, trust badges), and a page per integration with access, setup, tools/policies, risk badges, a test run, recent calls and uninstall. Account-dependent services can charge for calls and remain outside the default free task capabilities. Workspace setup, authentication limits and live-verification status: [connector guide](DATABRICKS.md).
- **External catalog discovery** (`sidecar/marketplaces.ts`, `src/marketplaces-page.ts`): optional source browsing supplements the curated integrations catalog. Search, pagination and connection review show provenance, exact endpoint/package, credentials, costs as unknown and compatibility limits. A single layout aligns the heading, navigation, toolbar and cards; external cards have explicit bottom-aligned actions. Source/publisher identity assets are shown separately from trust badges, with bounded authenticated image loading and passive SVG rendering. Imports require explicit consent, stay unverified/off and use the same installation/configuration/tool-policy lifecycle. Supported local packages require an exact version verified at least 14 days old and a compatible entry point; unsupported runtimes/authentication remain explicit. App-owned definition snapshots and bounded metadata cache contain no credentials or runtime state. Expired offline metadata cannot authorize imports; no automatic updates or activation. [Integration and verification guide](EXTERNAL-CATALOGS.md).
- **Channels** (`sidecar/channels.ts`): chat platforms answered while the app runs in the background, each declaring its secrets and a run-until-aborted function. Telegram runs `runTelegram` from `@vak/telegram` (shared with Projection's `npm run telegram`; a second poller on the same bot is reported, not crashed on). Off by default; each has its own model. Slack and Discord are listed as coming.
- **Shell** (`src-tauri`): starts the sidecar and hands the webview its address and token; menu-bar tray (Open, New chat, Quit); closing the window hides it while "keep running" is on; Dock click reopens; one instance only; launch at login; on quit the sidecar gets 4 s to stop channels. Links open in the system browser.
- **UI**: chats sidebar (date groups, rename, delete), the thread, a composer with a model picker (recent models plus installed local ones). The sidebar collapses (button or ⌘\\) and shows the app mark. Approvals appear in the chat as a card; tools used show as chips. Settings is a full page: Models (the provider's own model list from its key, plan, calibration), Providers (one card per provider: key, endpoint, status, model count), Channels (a page per channel), Appearance (System/Light/Dark, six themes, text size; surfaces follow), Chats (context window, engine notes, delete all), General (tray, login, model behaviour), About (version, data folder, log, shortcuts).
- **Canvas and Artifacts (app-only):** one sidebar Artifacts entry opens a searchable library of saved surfaces across chats, with type filters, sorting and pagination. Cards reopen the source chat and its live surface in a resizable canvas. Small interfaces stay in the conversation with Open in canvas; tables, charts, tabs, long code, forms over five fields and other large ones leave a reference card and open in the canvas (rule in `src/placement.ts`; growth promotes, nothing demotes). Closing the canvas returns each to its place with its live state. Tool-start shows progress in an open canvas; the first snapshot decides placement. Manual close suppresses reopening within that turn; a new turn can reopen it. History redraws do not auto-open artifacts. Preview/Text, Copy, Markdown download, a surface picker, full/split view and keyboard controls wrap the same live element, preserving drafts and validation. The host's session summaries include lightweight `surfaceSummaries` metadata; the library never previews form values. Design research and checks: [CANVAS.md](CANVAS.md).
- **Right-click**: the webview's menu never shows. Text fields keep the native editing menu; selected text gets Copy. Chats: Open, Rename, Delete. Your message: Copy, Edit as new message. A reply: Copy. An interface: Copy as text. Links and images: Open in browser, Copy address. Elsewhere nothing. Option-right-click keeps the inspector in dev builds.
- **Brand**: the Vakyartha Songbird and outlined full-name wordmark, imported from the original brand masters in `Vak/code`. The app icon uses the ivory bird and saffron throat on an indigo tile; the tray uses the supplied monochrome template. See `public/brand/README.md` for provenance.
- **Checking UI**: the window is WebKit; `scripts/webkit-check.swift` renders and scripts pages off-screen as the window does. Debug builds run `VAK_DEBUG_JS` in the window for probes.
- **Release**: `npm run desktop:build` bundles the sidecar, the Node binary and npm (for integrations) (`tauri.release.conf.json`); a build without them tells you so at start.

## 4. Voice: read aloud and dictation

- **Conversation mode** (`src/voice/conversation.ts`, ⌘⇧D or the waves button): the microphone stays open; `endpoint.ts` finds where each sentence ends from the input level against the room's noise floor. A sentence is transcribed by the dictation model and sent like a typed message, and the reply is read aloud. Speaking over a reply stops it (a higher bar and longer onset while the app speaks, plus echo cancellation, keep its own voice from counting). Esc, "stop listening" or "goodbye" ends it; "stop" alone only quiets the reply. Recordings stay in memory for one transcription. The system recognizer is not used here: it streams rather than taking a recording.
- **Approvals by voice** (`src/voice/approvals.ts`): in conversation mode a tool waiting on Ask is asked aloud, e.g. "Files wants to write file. Say \"allow write\" to allow it, or no." Only words heard from the microphone are resolved, by `@vak/core`'s deterministic `resolveAnswer`; no model takes part. Every approval counts as a change, so a bare yes is asked again. Consent must name a word from the tool's own name (agreement words are never one), voice allows once only, and after a second unclear answer the request waits on screen. The card stays and still works by click.
- **Choices by voice** (`src/voice/decisions.ts`): after a reply in conversation mode, the first choice it left (a comparison, a row of buttons, a button on each card) is asked aloud. "The cheaper one", "the second", "Hilton" are matched by `@vak/core`; the choice is read back ("Book hotel: Ryokan Sakura. Shall I?") and a yes activates the control through `<vak-surface>.activate`, the same path as a click. A longer sentence naming no option goes to the model as a message. Forms ask missing/invalid fields, show and read back the values, then submit through the same control activation path after confirmation; live microphone verification remains open.
- **One module, one switch.** The window imports voice only from `src/voice/index.ts` (read aloud, dictation, spoken form, settings) and the engine only from `sidecar/voice/index.ts` (its routes and keys). Settings → Voice → Use voice is the master switch: off, there is no microphone, nothing is read aloud and nothing reaches a voice provider; read aloud and dictation keep their own settings beneath it. It is on by default.
- **Read aloud** is for the person, not a tool the model calls, so it is not an MCP integration: `sidecar/voice/speech.ts` holds one adapter per voice provider (models, voices, the controls each model accepts, one synthesis call). Adding a provider is adding an adapter; its key, if new, is declared there and stored like any other secret.
- The engine asks every provider for 16-bit 24 kHz mono PCM and writes the WAV header itself; requests are capped at 4,096 characters and validated before anything is sent. The window splits a reply into sentence-aligned pieces, plays one while fetching the next, and keeps speed in the player. The model's style and slider options are passed through to the provider.
- **What is read** (`src/voice/speech-text.ts`) is the reply as a person would say it, not the text Copy gives.
  - Prose is read without code, links or markup.
  - Interfaces are read as content. A card is its title, subtitle, badge and body. A stat is "label, value, up 0.39%". A table is read row by row, at most six rows, then "and N more rows". A chart is one sentence giving each series' range, and an alert is its title and body.
  - Controls are skipped: buttons, inputs, selects, checkboxes, dates, dividers and images. Component names and actions are never read.
  - Everyday components are first lowered to the basic catalog with Projection's public `lowerSurface`.
  - Every line ends as a sentence, so the voice pauses there.
  - A dot inside a number never ends a sentence.
- **Language:** text is normalized to NFC. The reply's language is told from its script (Devanagari, Han, kana, Arabic, Cyrillic, Hangul) or from common words (en, fr, de, es, it, pt, nl); if the result is not clear-cut, it is left undefined.
  - Numbers, signs, percentages, ranges and the few phrases the app adds are said in that language.
  - English also spells out decimals ("0 point 3 9"), currency ("4 dollars 50") and abbreviations.
  - Other languages keep their own decimal comma.
  - An unknown language gets only language-neutral clean-up: no English words are inserted.
  - Voices that accept a language are told it with the Mac's region (`en` becomes `en-GB` on a British Mac):
    - Gemini through `languageCode`;
    - OpenAI's GPT voices through their instructions ("Speak British English");
    - ElevenLabs Flash and Turbo through `language_code`.
  - The language and whole sentences are how a voice chooses between words spelled alike ("a live event", "to live"). There is no pronunciation list.
  - **The voice follows the reply's language.** Each voice model may declare the languages it speaks (`VoiceModel.languages`): a Phonon pack speaks its own language, the multilingual pack speaks five, and hosted voices declare none (any).
    - When the chosen voice does not speak the reply's language, `voiceFor` reads with an installed voice that does. It looks at the same provider first, then other free local providers, and never at a billed provider the person did not choose.
    - A single-language pack is preferred to a multilingual one, and the voice name carries over when the new model has it.
    - If nothing fits, the chosen voice reads anyway, and a note afterwards names the pack to install.
    - Previews always use the voice being previewed.
- **Dictation** uses the same adapters (`transcribe`): the window records 16 kHz mono WAV, the engine forwards it (8 MB cap) and returns text.
  - Each transcription model may declare the language tags it honours (`SttModel.languages`). Settings → Voice offers only those; a model without a list offers the app's regional list.
  - The window sends the chosen language, or for "Same as this Mac" the Mac's own regional tag, narrowed to the most exact tag the model honours: `en-GB` becomes `en` for Whistle. A language the model does not know is not sent, and the model detects it.
  - The engine passes the whole tag to the adapter. OpenAI gets the bare language plus a prompt naming the region's spelling or script ("British English spelling", "Simplified Chinese characters"). Gemini is told the variant by name. ElevenLabs and Whistle get the bare language. The same path serves the browser and the app window. In a browser, the recognizer built into the window is the free default and needs no engine call. The app window's WebKit recognizer returns nothing, so there the first provider ready to transcribe is the default: Whistle, once installed. Gemini model lists come from its API.
- **Whistle** (`sidecar/voice/whistle.ts`) only transcribes, on this Mac's CPU, in seven languages (en, de, fr, es, it, nl, pl), and refuses others. Its engine is a prebuilt binary with no published source, so it is handled as untrusted:
  - its pack (the macOS arm64 engine plus weights, both Apache 2.0) is pinned to Hugging Face commits at least 14 days old and to each file's SHA-256;
  - it is checked before it is moved into `<data>/voice/whistle/<engine>-<weights>/`;
  - each recording runs as one process with an empty environment and, on macOS, with networking denied.
- Local first: a speech model on this Mac is the default and costs nothing; voice packs install only from a fixed list, through each adapter's own `install` (`POST /api/voice/install`). Hosted voices are opt-in and say that the text leaves the Mac and is billed. Voice choice, speed and auto-read are per window.

## 5. FinOps

**FinOps is app-only**, not a framework responsibility. Settings → FinOps charts turn duration, context composition, repeated context, generated output, provider token/cache usage and estimated API cost, with turn details, work-type/conversation filters, task/run attribution, editable model rates and CSV export. Schedule run details can load a numeric usage summary on demand; missing measurements and prices stay unknown, and estimates exclude tool/server charges and do not enforce a spending ceiling. The sidecar observes its provider requests and saves numeric telemetry locally; old sessions are explicitly reconstructed with unknown token usage and paid spend. Details and limits: [FINOPS.md](FINOPS.md).


## 6. Agent tasks (first implementation slice)

Tasks are app-owned product records linked to the host's canonical sessions and interactive surfaces. The UI adds task creation, scoped capabilities, compact activity, one-time approvals, explicit result review, cancellation and revision-checked deletion. Runs continue across navigation while the app is running. Finite cumulative execution limits span every continuation and restart; setup and details show run/request/tool/time budgets. Tasks persist a model spending policy: local-only by default, or explicitly acknowledged API charges. Required strict monetary ceilings are rejected before admission; operating and tool costs remain separate. Bound-field drafts persist locally and conflicting incoming values require an explicit choice. Completion requires a full-page user evidence review, tied to the current run and saved surface versions; it is explicitly not automatic verification. Acceptance leaves every surface interactive, and further actions create a continuation.

Tasks recover a provider-rejected tool generation only before any usable text/call, inside the same bounded execution. Attempts consume persisted request reservations; prior tool operations are not replayed by the runner. Partial streams and unrelated errors stop normally (ADR-016).

Task correction feedback includes a bounded inventory of saved surface IDs/root types. General framework authoring rules initialize supplied bound fields in canonical data and recommend patches for corrections; full render replacements and explicit empty lists retain their meaning. Syntax/binding repairs do not rewrite factual values or establish semantic verification (ADR-017). After layout/source checks pass, the app supplies neutral review prose through the public completion callback; final wording alone cannot trigger a repair generation. Original provider prose stays diagnostic data and acceptance remains a separate user decision (ADR-018). Typed layouts allow title/layout wrappers around independent form/table outputs, reject combined/ambiguous outputs, identify surplus IDs for correction and report blank comparison cells without inferring values (ADR-019). Optional user-supplied visible notices are bounded, saved in the existing result policy and checked against resolved output; they label content without certifying provenance or truth (ADR-020). Optional exact comparison assertions supply expected row identities and scalar values through setup JSON. Same-run checks reject mismatched displayed claims; assertions stay fixed across form changes and do not verify extra prose or their own provenance (ADR-022).

Tasks use response-oriented bounded runs: publishing a surface can be progress, while a response without tool calls ends that run. Product completion remains separate user review. The framework supplies in-process execution, immutable views, session ownership protection, action release and idle-session/transcript removal. No second surface store or native execution relay is introduced. **Schedule** opens an overview with search, lifecycle filters, sorting and starter ideas. A full-page composer creates immediate work or a one-time future run; details show activity, timing, permissions, expandable per-run records and result access. Permission waits yield the execution slot and reacquire it with fresh authority checks. Upcoming work supports pause/resume, Run now and time changes. Missed times are held for review; local execution needs the app running and computer awake. Repeating schedules, chains and sustained long-term execution remain unbuilt. Detailed behavior, limits, evidence and remaining work are in [MVP-SPECS.md](MVP-SPECS.md), [MVP-CHECKLIST.md](MVP-CHECKLIST.md) and [ADR.md](ADR.md).


### Checked task outcomes (2026-10-26)

Optional comparison contracts support caller-declared numeric criteria and bounded calculations (`divide`, `lte`, `gte`, `and`) alongside immutable supplied facts. The canonical criteria form submits `/criteria/<key>` values; validated submissions revise expected claims durably, while model-written data cannot revise the contract. The model authors corrections through normal framework APIs; the app checks the displayed claims and never rewrites the table. Fixed-only assertions remain fixed. See ADR-023.

Checked research requires a visible answer and limitations, plus a separate criteria form and source/quote/retrieved-at evidence table. The app records successful-read UTC timestamps with each run, supplies them to the model and exposes them in run details. Failed reads cannot issue receipts; displayed timestamps and quotations must match observed reads. Explanations remain interpretation for review, with structural validation rather than a claim of general semantic verification. See ADR-024.

### Task files, outputs and recovery (2026-10-26)

Task setup supports four explicitly selected bounded UTF-8 snapshots (`.txt`, `.md`, `.csv`, `.json`), with server-computed hashes and visible captured-input/freshness labels. It grants no ongoing folder access. Input content is sent to the selected task model as untrusted data. Optional Markdown exports go to private local task outputs, with one exclusive run filename, hash/size read-back and surface-version references. Details expose verification, download and explicit save retry. Changed/missing files and stale referenced surfaces block acceptance; retrying a save makes no model/tool calls.

Recovery records exact uncertain operation identities and a revision-bound user note before continuation; duplicate call IDs are not redispatched. Diagnostic retention is task-local: discard after each run, or expire the transcript after 1/7/30 idle days, checked at startup, after runs and hourly while idle. Task deletion removes owned content, outputs, temporary checkpoints and drafts. Downloaded copies and the explicitly listed shared/external records remain. See ADR-025/026 and EVALUATION.md for boundaries and evidence; general source truth and service-level exactly-once effects are not claimed.

Checked task API callers can optionally declare bounded `resultPolicy.initialValues`: safe bind paths to caller-supplied scalar defaults, asserted only in the first run. Task details expose these declarations. They never write surface values. Whole-result requirements are checked when authoring finishes, not after each edit; dependent checks wait for unambiguous surface roles. Checked tasks use the framework’s trusted transactional submission mode: one inline replacement/patch/removal change set, one complete validation decision, then canonical publication. Provider schema decoding enforces recursive component shapes when advertised; native-only providers still validate before admission. New surface IDs and descendant IDs are generated, and request schemas admit existing patch/remove targets only. Generated IDs remove initial reference bookkeeping; later edits use canonical IDs. Unchanged surfaces and interactions remain. Rejected/stale candidates publish nothing and cannot be exported. Other progressive chat/authoring remains available. Only known successful engine endings can save an output and request review; unchanged failed completion attempts stop early. Semantic interpretation still needs independent evaluation and user review.

### Source-backed checked workspaces

Selected bounded UTF-8 snapshots enter ordinary task context as untrusted source data with their filename/hash. Skills guide interpretation, calculations, form composition and requested views. Tables/charts/stat aggregates can map the same canonical records, and forms bind existing data pointers. The source-specific CSV bridge, derive/prepare tools and automatic criteria/report compiler are removed. Arbitrary per-record arithmetic uses an available governed computation tool or model-authored results that need independent checking; mapped aggregates alone do not guarantee source/calculation truth. Multiple surfaces, local edits, approvals, explicit result checks, exports and user review remain.

### Skill and schema assembly (2026-10-27)

The app system layer supplies identity, date and enabled skill descriptions. A counted selection loads relevant skill bodies; task callers add their explicit completion/input constraints. Projection then supplies only the active authoring protocol and typed tool descriptors. The former runtime compact/strict setting is removed. Native tools do not by themselves guarantee constrained decoding: complete candidates still undergo runtime validation. Optional caller data schemas cover known canonical structure, not a generated schema per request. Shared record data remains JSON with validated mappings and finite numeric projections.

Trusted local instruction loading consumes bounded model/answer steps, not external-operation budget. It grants no tool permission. Repeated form field names use full canonical pointer keys in submitted data; unique names keep short keys. Related views may share one surface; independently requested outputs and unrelated datasets stay separate. Catalog ingestion may apply its declared representation conversions, while caller data contracts are not coerced to obtain a pass.

### Built-in skill updates

New bundled skills seed once. Existing instruction files are not overwritten on startup. When a built-in differs from the installed body/description, Skills shows an Updates filter/badge and current/proposed preview. Updating verifies both offered and current fingerprints before replacing instructions and preserves enabled state. User edits remain until explicit replacement; removed skills remain removed. Catalog skills keep their reviewed pin; upstream auto-update discovery is not implemented.


### Governed capability dispatch (2026-10-27)

Projection validates supported native argument schemas before approval/execution, preserves explicit MCP error/denial status and rejects incomplete native generations or ambiguous tool names before external effects. Integration settings/metadata changes invalidate captured handles and chat grants; authority and cancellation are checked after approval. MCP HTTP work aborts on cancellation/timeout/close, response parsing is bounded at 8 MiB, and Retry-After consumes finite retries. Task receipt wrapping preserves structured results. Stale skill selection context fails explicitly; root skill review discloses supporting files that are not installed. [Pipeline review](PIPELINE-REVIEW.md) records the supported subset and remaining limits; these mechanisms do not certify model reasoning or external exactly-once execution.
