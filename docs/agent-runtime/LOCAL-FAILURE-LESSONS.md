## 2. Concrete lessons and required handling

| Lesson | New design requirement | Frozen regression scenario |
| --- | --- | --- |
| Provider `complete` can coexist with tool failures and no delivered result | Separate stream completion, run stop, requirement status and user acceptance in stored state and UI; numeric telemetry cannot authorize completion | A normal-ended response after failed tools retains failures/unknown requirements and cannot become verified complete |
| Many short tool attempts can accumulate without useful accepted evidence | Classify errors from trusted adapters: argument/schema, stale/missing resource, denied/revoked authority, unsupported capability, transient transport, resource exhaustion and uncertain dispatch; repeated unchanged failures consume one root diagnosis window | Repeated missing/stale Realm/schema failures trigger relevant state refresh/diagnosis or stop, not blind retry, automatic child creation or paid escalation |
| Aborting reasoning may leave a successfully created working copy | Preserve a returned operation outcome even if cancellation lands before the model answer; only a dispatched call with no returned response remains uncertain. Persist the owned Realm identity independently of stream/session lifetime, without copying its project path or arbitrary tool output, and require explicit discard | Cancel while create is in flight, then receive its success response: record `returned`, checkpoint the validated Realm UUID and do not replay. Reopen the task and confirm the UUID remains while the path/raw response are absent. Kill before any response: record `uncertain` and require reconciliation |
| Current audit records cannot reconstruct the entire failure path | Native events carry root/run/attempt/request/operation IDs, typed cause and initiator where actually known; unknown stays unknown | Inject abort at UI, deadline, resource, parent-death, transport and provider boundaries; each produces attributable durable cause or explicit unknown |
| Session/transcript removal can leave usage/tool records | Keep bounded non-content recovery/outcome references under their declared retention scope; deletion names what remains, and leaves a tombstone/missing-evidence status rather than an apparently verified historical result | Delete allowed diagnostic content, then inspect usage/job outcome and uncertainty without restoring raw content or falsely inferring success |
| Request assembly can dominate latency without external calls | Measure skill-selection, assembly/context admission, provider wait/generation, tools, checking, commit and delivery separately, including actual provider request identity | Use a frozen scripted assembly fixture and primary-local contract to locate earliest boundary; no prompt variants/timeout increase to manufacture a pass |

Selected steps in these installed records report 75,751 schema characters and 24,349–35,010 system characters; one recorded provider step took about 79.1 seconds. These are character counts and observed durations, not token counts or proof that schema size caused the delay. Source/installed/profile/request-envelope identity must be recorded before comparing against other captures with different schema sizes. Do not attribute latency to model size or solve it by spawning more agents.

Error categories must come from actual typed adapter/transport outcomes where possible. `ok: false` alone does not distinguish a rejected argument from a dispatched uncertain mutation. All attempts consume applicable root allowance; only a proven pre-dispatch failure avoids external-effect uncertainty. Classification cannot silently relabel an unknown dispatched write as safe to retry.

## 3. Independent retained provider-contract failure

The source-side record-view receipt `record-view-2026-10-29T05-02-16.884Z.json` in Projection's private contract evidence has two passing cases and one failed case: values `[100,70]`, `aborted` at 60.018 seconds, no diagnostics. A sanitized review of the local provider server log shows prompt processing reached 49 of 50 tokens; the request produced no observable framework event before the unchanged deadline, and the server logged the request finishing at 60.0019 seconds with a context-canceled termination. This locates the observed failure after nearly all prompt processing and before the framework received a usable result; it does not identify why generation stalled. The installed runtime was current at that time: local app logs report version 0.40.13, released by the upstream project on 2026-10-29 ([release record](https://github.com/ollama/ollama/releases/tag/v0.40.13)).

The prescribed frozen table-only contract was run once on 2026-10-30 with the same local model, three unchanged input cases and 60-second deadline. All three passed the exact table mapping and local edit checks in 12.100, 4.139 and 4.240 seconds. This demonstrates a current pass but does not explain the prior long stall or prove the stall cannot recur. Preserve the failed receipt; do not change the deadline or mark the provider reliability gate closed. This is separate from the three installed runs above.

Required handling: preserve the exact request/case and deadline, stop without canonical publication or fabricated output, distinguish provider-generation expiry from tool/effect uncertainty, and diagnose offline. Additional agents, parser variants or a larger timeout do not close the frozen failure. Matching primary-provider and original source/value/interpretation/interaction/output gates remain open.

## 6. Implementation test-run contention — 2026-10-29

During implementation, two ordinary parallel `npm test` runs produced different infrastructure-facing failures: first the DuckDB/sandbox case received exit 126 with “Trusted supervisor did not complete successfully”; then the FinOps local HTTP chat received 400 and the sandbox-pool failure case received the same 126 instead of its handler error. No assertions were changed. Each implicated suite passed in isolation (`app-database` 3/3, `finops` 7/7, `sandbox-pool` 5/5); the complete app suite first passed 270/270, then 271/271 after provider-policy parity coverage, 272/272 after the workspace bind-after-capture regression, and 273/273 after DuckDB 2 forward-read/write coverage. The latest run is on Node 26; the framework remains 412/412 under Node 26.

The evidence supports, but does not prove, that parallel test-file execution contends for shared OS supervisor/sandbox resources and can perturb unrelated local HTTP outcomes. This is not a user-outcome pass or evidence that real multi-job contention is safe. Keep both the parallel failures and serial pass. The runtime design must model one global sandbox/process capacity domain across roots, queue admission before helper launch, and return a typed resource-exhaustion or infrastructure failure instead of collapsing cleanup uncertainty into an unrelated handler error. Add a future saturation regression with independent roots and explicit global occupancy; do not make the test pass by weakening assertions or merely increasing concurrency limits.

## Helper capability version mismatch — 2026-10-30

After `vak-sandbox` moved its capability contract from 2 to 3 to report platform-specific nested filesystem exclusions, Vakyartha's `sandboxHelper()` probe still required 2. A fresh sandbox helper invocation succeeded, but app operations were refused before launch as “A supervised sandbox helper is required”; 19 app tests failed this way. The failures reproduced serially, so the first attribution to concurrent resource contention was wrong for this run. Updating the app's exact contract check to 3 and adding a regression for old/current/missing capabilities fixed the failures: the admin API test passed in isolation, then the full serial app suite passed 282/282. Keep this mismatch distinct from the earlier parallel-run contention failures; both demonstrate that shared capacity and exact cross-repository capability versioning need direct checks.

## Selected-file report budget exhaustion — 2026-10-26

The latest three retained local runs in `.vak/evaluations/agent-mvp/results/` were inspected by timestamp: `17-29-10.950Z-141e5632`, `17-34-57.875Z-3e2d14d1` and `17-40-38.659Z-cf77d009`. Each froze the same selected-file report outcome and used the local `qwen3.5:4b-mlx` provider. All three stopped at `max_steps` after 12 model requests. Independent-surface, exact-visible-value, current-surface-reference and verified-output-receipt checks failed in all three; source naming failed in the first and passed in the latter two. Required budget initialization failed in the latter two. All remain outcome failures; no check was loosened and no run was repeated.

This evidence shows why reaching a terminal response cannot stand in for completion and why a model/tool step cap needs its own durable stop cause. The task adapter now records `step_budget_exhausted` for the framework's typed `max_steps` result, keeps the run failed, creates no output receipt and does not auto-retry. Its focused regression checks persistence after reopen. That is safer diagnosis, not a repair of the report, surfaces, budget initialization or output path. The original frozen checks remain open and must pass before claiming task outcome closure.


## Desktop containment integration failures — 2026-10-30

The first contained desktop smoke reached its actual success marker, then the checker looked for the uploaded file under the old app-data root instead of `worker/attachments/`. The checker now reads the actual worker namespace and retains the exact uploaded byte and permission checks. The first Linux Node canary stopped before script execution because OpenSSL tried to read `/etc/ssl/openssl.cnf`, outside the worker grants. An explicit `OPENSSL_CONF=/dev/null` disables ambient host configuration without widening read access. The same frozen canary then passed protected-file read/write denial, a real listening-loopback connection denial, private channel delivery and positive worker-directory writes. Both earlier failures remain mechanism evidence, not user-outcome failures that can be erased by broader suite passes.


A subsequent startup refused the private handshake because the packaged helper was killed before running. Direct `--version` on that copied helper exited 137 while the build output ran; signature verification alone passed. The macOS kernel log recorded load code-signature error 2 for the packaged helper. The packager had overwritten executable files in place. It now copies Node/helper binaries to fresh staging files and atomically renames them. The replaced helper runs, its SHA-256 equals the build source, and the full contained native WebKit smoke passes. This addresses the observed packaging boundary without expanding worker authority or relaxing startup checks.


## Native start did not reserve execution capacity — 2026-10-30

The old native `StartAttempt` changed root status without a run record or generation reservation. Replacing it with atomic root/run/lease admission exposed five fixture failures: three tests used a metadata-only empty profile while starting runs, one held multiple running roots plus an extra generation request beyond its profile, and one workspace rebind sequence reused execution capacity without supervisor exit settlement. Execution tests now configure capacity explicitly and settle only with a trusted test supervisor receipt. Unconfigured start remains refused; revocation/cancellation alone still does not refund a live execution charge. New regressions retain those distinctions. Product task supervision and native scheduler cutover remain open.

## Native lifetime and Linux stream recognition — 2026-10-30

The real private-channel test added coverage absent from earlier byte-write canaries. Linux Node could not recognize descriptor 3 (`ERR_INVALID_FD_TYPE: UNKNOWN`) because seccomp denied its socket-type inspection. The sandbox now allows only interactive descriptor 3’s `SOL_SOCKET/SO_TYPE` query; C probes retain explicit denial of other options/descriptors, creation/pairs, connect and descriptor passing. The original real Node test now passes through cancellation, actor reopen and exact native settlement. Earlier tests using null stdin now explicitly keep the owner pipe alive until target exit: under the corrected lifetime contract EOF cancels, regardless of target cooperation.

The helper tests also exposed runtime shutdown retained by uncancellable async stdin, plus fixtures with non-private temporary directories and a missing required read grant. The implementation uses a bounded std-thread input bridge; fixtures now satisfy the existing owner-only/grant rules. A native macOS path comparison initially rejected the equivalent `/var` and `/private/var` parents; preparation now returns a canonical native parent. An early native receipt test also used a fixed start ID while its helper generated one; the fixture now creates the exact named request. No cleanup, identity, containment or original outcome expectation was weakened. These mechanism repairs do not close the retained report outcome failures or enable native product task execution.
